# Known Gaps — Read Before You Trip Over Them

**Current state.** Real, current, and they bite silently. Each row names the file that proves it. Verify before trusting; delete the row when you close it. **Numbers are stable and never reused** — a missing one is a gap that was closed, and renumbering would silently repoint every `known-gaps #N` in the tree at a different gap.

| # | Gap | Where | Consequence |
| :---- | :---- | :---- | :---- |
| 1 | **Tenant scoping is applied by hand.** `tenantScope()` is the shared helper and is used across services, but there is **no Prisma middleware or `$extends`** — nothing forces a query to call it. | `libs/common/src/utils/tenant-scope.ts` | A forgotten `...tenantScope(ctx)` is a cross-tenant data leak, not a bug. **`findUnique({ where: { id } })` cannot express the filter at all** — always `findFirst` + scope, and let a miss be `NOT_FOUND`, never `PERMISSION_DENIED`. |
| 2 | **`otps.code_hash` and `two_factor_backup_codes.code_hash` use SHA-256** where a slow KDF is the better fit (§8.1). Both columns are already `VarChar(255)` to accommodate one. | `apps/auth-service/src/modules/otp/otp.service.ts` (`hashToken(code)`), `apps/auth-service/src/common/utils/crypto.ts` | A 6-digit code is ~20 bits — offline-guessable if the table leaks. `maxAttempts` + short expiry are the online defence today. |
| 3 | **Deferred ingestion jobs are never resumed.** When a tenant hits the AI cap mid-ingestion the processor returns the job to `QUEUED` and the document to `PENDING`, and the BullMQ job completes successfully — deliberately, so the deferral does not burn the retry budget. `drainDeferred()` exists to re-enqueue them at cycle roll and **has no caller**. | `apps/ingestion-service/src/modules/ingestion/ingestion-queue.service.ts` (`drainDeferred`), `ingestion.processor.ts:190` | A document deferred at the cap stays `PENDING` and unindexed forever. `POST /ingestion-jobs/:id/retry` is the manual hatch; nothing automatic exists. |
| 4 | *Closed.* At most one live ingestion job per document is now enforced by `ingestion_jobs_one_live_per_document`. The number is kept rather than reused so citations of `#5` and above stay valid. | — | — |
| 5 | **The `users` super-admin CHECK constraint was never applied.** `apps/auth-service/prisma/schema.prisma:151` says `organization_id` is *"kept in lockstep with isSuperAdmin by a DB CHECK constraint added via migration: (organization_id IS NULL) = is_super_admin"*, There are no migrations, and the seeder's DDL block creates exactly one CHECK on `users` — `users_locked_until_requires_lock` — which is a different constraint. `development-conventions.md` §7 used to name this constraint as one of two exceptions, which is how a constraint that does not exist was documented as existing for as long as it was; §7 now points at the seeder blocks instead (ADR 0039), so the block is the only place to read its absence. | `apps/auth-service/prisma/schema.prisma:151`, `apps/auth-service/src/modules/prisma/database.seeder.ts` (the raw-DDL block), `docs/development-conventions.md` §7 | Nothing prevents `organization_id = NULL` with `is_super_admin = false`: a row with no tenant that is not a platform account, which every tenant filter treats as unreachable rather than as an error. Any code reasoning "super admins have no tenant" — e.g. the `!== undefined` guard in `AuditPublisher.record` — is relying on convention, not on the database. |
| 6 | **`?search=` is advertised on five list routes and honoured on none of them.** `SearchPaginationDto` puts `searchTerm` on the wire and into Swagger, but `toSearchFilter(page.searchTerm)` is called in exactly two services — `documents.service.ts:314` and `tickets.service.ts:120`. The DTOs for ingestion jobs, document flags, audit logs, ticket messages and feedback all extend it and all ignore it. | `apps/api-gateway/src/common/dto/rest/search-pagination.dto.ts` (the base), and the five `List*QueryDto` classes extending it | A caller filters a worklist by `?search=`, gets an unfiltered page back, and reads it as "no other matches exist". Silently dropping a documented filter answers a different question than the one asked — the failure `listDocumentFlags` explicitly refuses an unknown flag type to avoid. |
| 7 | **`scheduler-ownership.e2e-spec` fails intermittently on a full auth-service run.** Three sightings across three docs, each on `npm run test:e2e:auth` with every other suite in the run, each passing in isolation on the next attempt, and each with the session's changes nowhere near a scheduler. The suite asserts BullMQ queue isolation against a **shared real Redis**, and every service's e2e suite uses the same instance — `bootstrap.ts` already documents the class of problem for ingestion ("WORK must not escape its test"). | `apps/auth-service/test/modules/scheduler-ownership.e2e-spec.ts`, `apps/auth-service/test/utils/bootstrap.ts` | A red suite that is green on re-run teaches the team to re-run. **Next sighting, capture before re-running:** which case failed, whether another suite in the same run had touched `SCHEDULER_QUEUE`, and the Redis key set at failure — three sightings with no captured detail is why this is still a maybe. |
| 8 | **Three writes move `roles.user_assigned` without evicting the cache that shows it.** `GET /roles` caches `userAssigned` for five minutes per tenant. `PUT /users/:id/roles` and `DELETE /users/:id` now evict it; **`POST /invitations/accept` cannot** — `CacheInvalidationInterceptor` derives the tenant from the request context and returns early without one, and that route is unauthenticated by design. | `apps/api-gateway/src/modules/invitations/invitations.controller.ts` (`accept`), `apps/api-gateway/src/common/interceptors/cache-invalidation.interceptor.ts` | After an invitation is accepted, the roles screen shows a stale `userAssigned` for up to five minutes, and a cached hit is indistinguishable from a fresh read. Covered by TTL, which is the same trade that interceptor already accepts for a platform Super Admin writing into a tenant. Closing it needs an eviction path that does not depend on a caller — the NATS consumer that class mentions. |
| 9 | **The export family is named for one of its four kinds.** `AnalyticsExport`, `analytics_exports`, `AnalyticsExportKind`, `ANALYTICS_EXPORT_QUEUE` and `apps/ticket-service/src/modules/analytics/analytics-export.*` now carry `TICKET` and `AUDIT_LOG` exports, which read live tables and are not analytics. The shared thing is the LIFECYCLE — one status machine, one queue, one processor, one poll route — which is why they share a table rather than getting two more. | `libs/common/src/configs/analytics.config.ts` (`AnalyticsExportKind`), `apps/ticket-service/prisma/schema.prisma` (`AnalyticsExport`) | A reader looking for the ticket export finds it under analytics, and a table called `analytics_exports` holds audit-log rows. Renaming to `Export` is ~18 files outside generated code plus a proto regeneration and the enum-bridge registry — deferred deliberately, not overlooked. Do it as its own change, or the half-done state sits under three features. |
| 10 | **Nothing reports which roles still hold a RETIRED permission code.** A code removed from `PERMISSION_CODES` is deliberately left in the `permissions` table, because tenant custom roles may still reference it and dropping the row would cascade that grant away silently (ADR 0038). `SeedSummary.retiredPermissionCodes` names the CODES at boot; nothing names the roles. | `apps/auth-service/src/modules/prisma/database.seeder.ts` (`seedPermissions`), `apps/auth-service/src/modules/roles/roles.service.ts` (`listPermissions`) | After a retirement an operator can see that a code is dead and not who is still carrying it — so a role keeps advertising a capability no guard will ever satisfy, and nobody is told which roles to edit. The query is one line: `role.findMany({ where: { permissions: { some: { code: { in: retired } } } } })`. Latent until the first removal — the table and the array match exactly today. |
| 11 | **A re-run re-embeds the whole document and is billed for it.** Every entry into `process()` runs `writeChunkRows`, which deletes and recreates every chunk row, so the `vector_point_id IS NULL` filter in `embedAndUpsert` matches the entire document and no embedding work carries across runs. A retry after a failure in the last batch of a 400-page handbook re-embeds all 400 pages, metered as `EMBEDDING` against the tenant's budget. | `apps/ingestion-service/src/modules/ingestion/ingestion.processor.ts` (`writeChunkRows`, `embedAndUpsert`) | The tenant pays twice for one document, and the charge is invisible — it looks like ordinary ingestion spend. Distinct from #3, which is about a deferred job never being re-enqueued at all; this is about what a run that DOES happen redoes. Resuming across runs needs the point ids to survive `writeChunkRows`, which is a different shape of pipeline, so `ingestion-pipeline.e2e-spec` test 19 pins the current cost rather than asserting it away. |
| 12 | **`ticket_assignments.assigned_by_id` is nullable for a case that cannot occur.** The column says *"null when the system assigned it"*, but `writeAssignment` is its only writer and takes `requireActor(context)` — and `load` refuses a caller with no identity, so no assignment can happen without an actor. Same shape as `ticket_status_changes.changed_by_id`, which was made `NOT NULL` for exactly this reason when it was added. | `apps/ticket-service/prisma/schema.prisma` (`TicketAssignment`), `assignments.service.ts` (`writeAssignment`), `assignment.proto:16` (`optional string assigned_by_id`) | A reader takes the null as a supported case and writes a branch for it — `assignment.mapper.ts` already has one (`?? undefined`). Closing it is a four-file chain: schema, proto, mapper, gateway DTO. Deliberately not done inside doc 47, which is about ticket reads and the status history; the comment was corrected in place so it no longer misleads. |
| 13 | **`ingestion-pipeline` test 6c fails intermittently on a full run, and it is NOT gap #7.** Both fail only on a full run and that is where the resemblance stops. #7 asserts BullMQ queue isolation against a **shared real Redis** — genuine cross-suite interference. 6c hangs a `downloadObject` promise it owns and then `waitFor`-polls **its own job row in Postgres** until the status reads `PARSING`; it touches no queue and opens no Redis connection. Its failure is a **poll budget sized for an idle process**, expiring when `--runInBand` gives the box more to do. One sighting. | `apps/ingestion-service/test/modules/ingestion-pipeline.e2e-spec.ts` (test 6c), `@synapsedesk/common/testing/wait` | Filed separately on purpose: merging it into #7 would point the next person at Redis for a test that never opens a connection to it, and merging two rows later is cheap while un-merging a generalisation that has already sent somebody to the wrong system is not. **Next sighting, capture before re-running:** the elapsed time at failure and what else was running. Note the capture instruction on #7 is scoped to one spec, which is probably the bug — the information it protects (which suites were in the run) is lost either way. |
